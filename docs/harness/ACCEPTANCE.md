# Harness acceptance suite (gate G10)

`bash eval/harness_acceptance.sh` is the one command that answers "does this checkout of
the harness still work, and is it the build that ran?". It writes every piece of evidence
under `runs/harness-acceptance/<utc-stamp>/` and prints a PASS/FAIL line per stage plus
`HARNESS ACCEPTANCE: PASS|FAIL` (exit code 0/1). It never rebuilds or edits the Forge
checkout: sources are compiled into an isolated directory and the pinned engine classes
are only read.

A full run compiles once, then runs the later stages as four child runs side by side (`OUT/part<n>/`, their
summaries merged into `OUT/summary.txt`), each JVM held to one core's worth of GC and compiler threads, with the
keyword sweep split over `SWEEP_SHARDS` (2) JVMs: about 8 minutes on an idle 4-core machine, against 11 one stage
after another, and up to 15 when other game JVMs share the cores (timings with their run directories: PR #301).
The longest group is pytests beside the canaries. `ACCEPTANCE_JOBS=1` runs every stage in one process with the
sweep in one JVM.

The parent reads each child's exit status and requires a PASS or FAIL line for every stage it handed the child,
so a child that dies part way fails the run instead of leaving only the PASS lines it wrote before it died.

`FORGE_HOME`, `JAVA_HOME`, `GAME_CAP_MS` as usual; `HARNESS_DEPS_FILE` reuses a saved
dependency classpath when Maven is unavailable.

## Re-pinning

`eval/harness_acceptance.expected` holds the canary outcomes and the ownership baseline.
Change a number only together with the commit that legitimately moved it, and say why in
that commit. Re-pinning to make a run pass is the failure mode this file exists to prevent.

The canary games are not the same on every OS: seed 42 plays to a different decision count on
Linux than on the reference Mac at the same commit (cause not found yet; JDK, CPU count, locale
and timezone are ruled out). A key prefixed with the lowercase `uname -s` (`linux.floor.decisions`)
wins over the plain key on that OS, and the plain keys are the Mac's. Pin an OS only from a run on
that OS, reproduced, with the same note a re-pin needs.

## What acceptance does not prove

- Strategic quality or fairness of play. The loopback fake model answers by a fixed
  policy (`eval/fake_model_server.py --policy`: pass, first, simulate, random, empty, garbage).
- Hidden-state noninterference beyond the fixtures in `SeatObservationTest` (see
  PLAYER-HARNESS.md gates G1/G2); the canary games run legacy profiles.
- Paid-model behaviour: no external endpoint is contacted. The loopback exemption in the
  egress gate is what makes the faketool stage possible without consent flags.
- Model ownership of every strategic decision: `[OWNERSHIP]` in the javatests line reports
  how many silent Forge-AI strategic hooks remain reachable (OWNERSHIP.md).
- Every mechanic in a full game. The javatests stage includes `KeywordSurfaceSweepTest` (each Forge keyword's
  plays reachable from the menu and played once), but the states between plays (combat, upkeep, death, end step)
  come only from games: run `bash eval/keyword_gauntlet.sh` after a passing acceptance run (28 zero-cost games;
  `eval/gauntlet_scan.py` exits non-zero on any harness defect).
